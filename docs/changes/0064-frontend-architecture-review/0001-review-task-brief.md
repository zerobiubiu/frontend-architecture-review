## 一、任务背景

当前项目是面向 Binance Stocks 官方支持证券的交易执行与管理系统。

后端当前基线为 **3.0.0**，技术栈：

- Bun
- TypeScript
- Hono
- PostgreSQL 18.6
- Drizzle
- Zod
- decimal.js
- @binance/stocks
- @binance/wallet

后端采用模块化单体架构，HTTP API 与独立 Worker 分进程运行。

目前后端已经实现了账户管理、证券查询、行情读取、单笔交易、批量任务、订单核对、账户核对、账本、操作回执、权限管理和平台风险控制等能力。

当前没有可直接使用的前端工程。

本次任务的目标是审查拟采用的前端技术架构是否能够与现有后端真实实现兼容，并识别前端开发前必须解决的问题。

### 任务 3：重点审查 SSE 实现

这是本次审查的 P0 重点。

后端已经提供两条 SSE：

- `GET /api/v1/events`
- `GET /api/v1/market/quote-stream`

请直接检查对应源码，确认：

#### 业务 SSE

- 实际事件结构。
- 资源类型。
- 消息载荷。
- 事件触发位置。
- 是否包含资源 ID。
- 是否包含账户 ID。
- 是否包含事件时间。
- 是否包含事件序号。
- 是否存在重复事件。
- 是否存在事件丢失。
- 重连行为。
- 连接鉴权和授权。
- 连接数限制。

#### 行情 SSE

- 实际 URL 参数。
- 是否支持多个证券。
- 是否一个证券对应一个连接。
- 是否支持订阅变更。
- 首次连接是否返回快照。
- `quote` 和 `status` 的真实结构。
- 报价时间和精度。
- 行情状态。
- 后端补读逻辑。
- 账户隔离。
- 连接数限制。

#### 前端实现可行性

验证以下方案是否可行：

```text
Business SSE
    ↓
Event Dispatcher
    ↓
TanStack Query Invalidation
    ↓
REST API
    ↓
Authoritative Snapshot
    ↓
React UI
```

行情：

```text
REST Snapshot
    ↓
Market SSE
    ↓
Event Parser
    ↓
Market Store
    ↓
React UI
```

特别检查：

1. EventSource 是否可以直接使用现有 Cookie 会话。
2. 是否存在 CSRF 或 Origin 配置问题。
3. SSE 是否支持账户切换。
4. 多标签页是否会超过连接限制。
5. 重连后是否需要重新读取全部相关资源。
6. 是否有必要增加 SSE 事件版本或资源类型字段。
7. 是否存在需要后端补充的多证券订阅能力。

不要自行假设 SSE 支持事件补播或历史游标。

如果后端没有提供，必须明确标记。

## 四、必须重点分析的五个问题

以下五项是本次审查的最高优先级。

### P0-1：SSE 数据与前端 Query 缓存的一致性

需要明确：

- 后端发出什么事件。
- 前端如何识别事件。
- 事件对应哪些资源。
- 哪些 Query 需要失效。
- 是否需要重新读取多个接口。
- 重连后如何恢复。
- 如何避免频繁刷新。

### P0-2：未知订单结果的跨刷新恢复

需要明确：

- 原订单标识存储在哪里。
- 页面刷新后如何找回。
- 如何从 `/operations` 恢复。
- 如何区分订单状态和原操作回执。
- 如何避免重复提交。
- 如果操作没有持久回执，前端应该如何处理。

### P0-3：API 契约完整性

需要明确：

- 现有契约是否可以直接用于前端。
- 是否存在运行时与静态声明差异。
- 是否需要补充 SSE 类型。
- 是否需要共享 Schema。
- 是否需要生成 API 客户端。

### P0-4：账户与金融数据的真实性表达

需要明确：

- 当前资产与旧快照。
- 已确认零值与未知值。
- 官方库存与本地名义持仓。
- 预留费用与实际费用。
- 本地订单与官方订单。
- 核对完成与核对一致。

不能让前端产生错误的金融语义。

### P0-5：会话安全与权限隔离

需要明确：

- Cookie 和 CSRF。
- 迟到 401。
- 账户切换。
- 用户禁用。
- 多标签页。
- SSE 授权。
- 缓存清理。
- 管理员和交易员权限差异。

## 七、执行约束与独立技术审查原则

本次任务不仅是验证前端技术架构能否与现有后端兼容，还必须对前端技术提案本身进行独立、客观的技术审查。

**现有前端技术栈和架构设计均属于待验证方案，不是预先确定的最终决策。**

审查过程中必须保持技术独立性。不能默认提案中的技术选型正确，也不能为了证明现有方案合理而刻意寻找支持证据、忽略缺陷或弱化风险。

### 7.1 独立技术审查与反向论证

你拥有充分的技术否决权。

如果发现现有技术选型存在实际问题，必须明确提出反对意见，并给出有依据的替代方案。

不得为了技术栈统一、开发者偏好、框架品牌或保持现有设计不变而牺牲项目实际需求。

至少对以下技术进行独立审查：

**1. Astryx**

- 是否真正适合整个交易执行与管理平台？
- Beta 阶段是否存在影响生产使用的风险？
- 基础组件是否足以支撑完整业务界面？
- 表格、复杂表单、日期选择和弹窗等能力是否满足实际需求？
- 是否存在组件定制成本过高的问题？
- 是否应该考虑 MUI、Chakra UI、其他成熟组件库，或者组合式组件方案？
- 是否应该采用 Astryx 作为主设计系统，还是只借鉴其设计规范？

**2. TanStack Query**

- 是否适合当前 REST + SSE 的数据同步架构？
- Query Invalidation 是否足以满足订单、任务和账户数据的一致性要求？
- 是否存在缓存竞争、过期快照覆盖新数据、重复请求等问题？
- 是否需要更精细的缓存更新和资源同步机制？
- 是否存在更合适的服务端状态管理方案？

**3. SSE**

- 当前两条 SSE 是否足以满足实际业务需求？
- 连接数量限制是否影响实际使用？
- 缺少事件补播、历史游标和中间事件必达保证是否会产生业务风险？
- EventSource 自动重连是否足够？
- 是否需要后端增强 SSE？
- 是否存在不能通过 SSE + REST 安全解决的场景？
- 是否有必要在特定业务场景使用其他通信方式？

不得因为后端已经使用 SSE，就默认 SSE 一定是最优方案。

**4. Zustand**

- 是否真的需要独立的行情 Store？
- 是否存在 TanStack Query 与 Zustand 职责重叠？
- 是否需要 Vanilla Store 或 useSyncExternalStore？
- 是否存在过度拆分状态管理的问题？
- 是否有更简单的状态管理方式？

**5. TanStack Table**

- 是否足以满足订单、成交、持仓、账本和管理数据的表格需求？
- 列固定、列调整、单元格编辑、复制粘贴等功能的自研成本是否合理？
- 是否应该考虑 AG Grid 或其他 Data Grid？
- 是否需要 TanStack Virtual？
- 是否应该优先通过后端分页解决数据量问题？

**6. React Hook Form + Zod**

- 是否适合当前复杂批量任务配置？
- 是否能够合理处理动态字段、条件字段和异步校验？
- 是否存在复杂表单状态管理问题？
- 是否值得重新评估 TanStack Form？

**7. Native Fetch + Backend Contracts**

- 当前公开客户端契约是否足以支撑完整前端？
- 是否需要共享 Schema？
- 是否需要 Hono RPC？
- 是否需要 OpenAPI？
- 是否存在更合理的前后端类型安全方案？

**8. 其他技术及架构**

- 是否存在不必要的技术依赖？
- 是否遗漏真正必要的基础设施？
- 是否存在多个技术承担相同职责？
- 是否存在过度设计？
- 是否有更简单、更可靠、长期维护成本更低的实现方式？

以上审查范围不是封闭列表。发现其他值得质疑的选型，也必须主动提出。

### 7.2 必须比较替代方案

对于存在争议或明显风险的技术选型，必须比较至少两个可行方案。

比较维度：

- 与当前后端的兼容性。
- 功能覆盖程度。
- 交易业务正确性。
- 数据一致性。
- 运行时性能。
- 开发复杂度。
- 定制能力。
- TypeScript 类型安全。
- 社区成熟度。
- 版本稳定性。
- 长期维护成本。
- 对现有后端的改造要求。

比较必须结合当前项目实际需求，不要只罗列框架功能。

如果替代方案明显更好，应当明确建议替换。

如果原方案更好，也必须解释其他方案为什么不适合。

不要求为了比较而强行替换技术。

### 7.3 严格区分事实、推断和待验证事项

所有审查结论必须区分以下四类：

| 类型 | 定义 |
|---|---|
| 已验证事实 | 有当前源码、实际测试或明确契约作为依据 |
| 技术推断 | 根据实际源码和架构推导出的风险或结论 |
| 待验证事项 | 当前资料和源码不足以得出结论 |
| 外部技术判断 | 根据第三方官方文档、版本信息和生态情况得出的结论 |

具体要求：

1. 不得将推断描述为已经复现的问题。
2. 不得将尚未测试的组件能力描述为已经验证。
3. 不得仅凭技术名称判断其适用性。
4. 不得仅凭静态类型声明推断运行时行为。
5. 对需要浏览器原型、压力测试或实际联调才能判断的问题，明确列出验证方法。
6. 对第三方技术的版本、兼容性和稳定性问题，尽量使用对应版本的官方资料验证。
7. 对无法确认的问题明确标记为待验证，不得自行补全事实。

### 7.4 禁止迎合式审查

不得默认以下结论：

- Astryx 一定适合当前项目。
- TanStack Query 一定能够解决所有实时数据同步问题。
- SSE 一定满足全部实时通信需求。
- Zustand 一定是必要的。
- TanStack Table 一定比 AG Grid 更合适。
- React Hook Form 一定优于 TanStack Form。
- Native Fetch + Backend Contracts 一定是最优 API 方案。

这些都必须经过独立分析。

如果发现技术选型不合理，可以直接给出：

- 不建议采用。
- 有条件采用。
- 建议替换。
- 暂缓采用。

不要求必须找到问题，但必须真正尝试证伪现有方案。

**不能为了让所有技术选型通过而降低审查标准，也不能为了体现审查价值而虚构缺陷。**

### 7.5 必须提供独立的最终技术决策

最终报告必须单独提供一份不受原提案约束的技术选型结果。

至少包含以下表格：

- 保留的技术。
- 替换的技术。
- 新增的技术。

- 暂缓引入的技术。

### 7.6 最终技术决策原则

最终技术方案按照以下优先级进行选择：

1. 交易业务正确性。
2. 数据一致性与状态可追溯性。
3. 安全性与权限隔离。
4. 运行稳定性。
5. 与现有后端的兼容性。
6. 开发与长期维护成本。
7. 性能。
8. 技术栈简洁性。

技术生态统一、框架流行程度、品牌知名度和开发者个人偏好不能凌驾于以上目标之上。

最终目标是选择真正适合当前交易执行与管理系统的技术方案，而不是证明原有提案正确。

### 7.7 执行范围与禁止事项

本次任务只允许进行：

- 源码阅读。
- 代码搜索。
- 项目结构检查。
- 类型检查。
- 现有测试执行。
- 只读接口与架构分析。
- 可行性验证。
- 第三方官方技术资料查阅。
- 审查报告编写。

**禁止执行以下操作：**

- 修改后端业务代码。
- 修改 API 行为。
- 修改数据库 Schema。
- 创建或执行数据库迁移。
- 修改订单状态机。
- 修改任务执行规则。
- 修改官方交易 SDK 调用逻辑。
- 修改 Worker 执行逻辑。
- 修改安全和权限机制。
- 引入新的生产依赖。
- 为了配合前端方案而重构后端。
- 自动进入前端工程开发。
- 自动实施审查过程中发现的后端修改建议。

如果验证过程中发现需要修改后端，必须先记录问题、源码依据、影响范围和修改建议，不得直接实施。

### 7.8 项目工作区保护

2. 确认现有未提交修改。
3. 不覆盖、不删除、不重置用户已有文件。
4. 不修改现有业务源码。
5. 不执行具有破坏性的清理操作。
6. 仅在指定报告路径创建或更新审查报告。
7. 如果报告文件已经存在，先检查其内容和历史修改，避免覆盖其他人的工作。

如果现有测试需要数据库、官方 API 凭据或外部服务才能运行，不得擅自连接真实资金账户或执行真实交易。

只运行安全、只读且不会产生实际交易副作用的验证。
