# 项目与后端概览

- 状态：现状参考。
- 基线：后端 **3.0.0**；依据 2026-11-09 的项目源码版本信息、产品范围及现行架构与接口资料整理。
- 范围：本文独立说明项目定位、业务能力、后端组成、完整接口范围、关键状态、执行规则与当前边界，所需解释直接写在正文中，无外部阅读跳转。不包含前端选型、界面设计或实施指导；能力描述不等同于部署或真实资金交易验收。

## 1. 项目是什么

本项目是面向 **Binance Stocks 官方支持证券的交易执行与管理系统**，证券范围包括普通股、ETF 等，以官方证券目录为准，不设置固定证券白名单。

核心业务是管理账户与交易意图，执行单笔订单和持续运行的批量任务，追踪官方订单、实际成交、费用与库存，并形成可追溯的本地业务记录。它不是以 K 线、技术指标、选股、策略研究或回测为核心的行情分析终端，也不包含加密货币、衍生品或代币化交易。

当前分支交付后端工程及业务资料，没有可直接使用的前端工程。后端连接 Stocks 正式环境，不包含本地撮合、虚拟资金或可供用户使用的 Testnet／Demo 模式。

## 2. 使用者与权限

系统区分交易员和平台管理员。一个用户只有一种角色，业务数据同时关联交易账户与所有者。

|角色|业务范围|权限边界|
|---|---|---|
|交易员|管理本人活动账户与凭据；查询资金、持仓和业务记录；提交单笔订单、撤单及批量任务；控制本人任务|当前每名交易员只有一个活动交易账户，不能访问其他所有者的数据|
|平台管理员|管理用户与授权；查看跨用户业务；限制账户；暂停、停止、核对任务；配置平台限额、费用预留政策与急停；查看审计和服务状态|不能直接买卖、直接撤单、编辑或启动／继续交易任务，也不能读取 API Secret 明文|

管理员的任务控制仍可能推进交易员此前已授权的自动撤单规则，因此监管操作并非全部只读。身份、角色、所有权和业务动作权限由后端执行校验。

平台用户是本站登录身份，交易账户是本站保存官方凭据和业务归属的记录，两者不是 Binance 官方身份本身。创建交易账户只是在本站登记凭据，不会创建一个新的官方账户；初始交易关闭，连接尚未验证。管理员也不能代交易员创建账户、更换凭据或执行交易员专用的连接检查，但可以进行资产同步、账户核对和订单核对。

`canManageAdmins` 是管理员管理其他管理员的专项权限，不是第三种角色。普通管理员不能自行取得该权限；最后一位仍处于活动状态且具有该权限的管理员受到保护，不能被禁用或撤权。角色创建后不能变更，公开接口没有改用户名、管理员代改密码或删除用户的动作。禁用用户、变更相关管理权限会撤销其会话，重新启用不会自动恢复任务。

## 3. 后端由什么组成

后端采用 **Bun、TypeScript、Hono、PostgreSQL 18.6 和 Drizzle**。Zod 承载公开输入校验，decimal.js 承载精确十进制计算；官方接入使用 `@binance/stocks` 与 `@binance/wallet`。

|组成|职责|
|---|---|
|HTTP API|会话与权限检查、输入校验、业务查询、交易与管理操作入口，以及对外事件推送|
|独立 Worker|持续推进批量任务，核对原订单与成交，执行已配置的挂单策略和恢复流程|
|PostgreSQL|持久化用户、账户、订单、成交、任务、预留、名义持仓、账本、操作回执与审计等数据；以事务和行锁协调业务一致性|
|统一官方接入层|组织 Stocks／Wallet 请求、签名、行情与私有订单流，将官方数据转换为项目使用的业务证据|

工程采用模块化单体结构，API 与 Worker 是独立运行进程。`server` 负责 HTTP，`services` 负责应用用例及数据库事务，`domain` 负责不依赖网络、数据库或 SDK 的金融规则，`api` 负责官方 SDK 适配。

交易执行不依赖页面持续在线。关闭页面、退出登录或浏览器断开，不会自动停止任务或撤销订单；服务器停止运行也不等于交易所挂单已撤销。

### 业务对象之间的关系

|对象|含义与关联|
|---|---|
|交易账户|关联本站所有者、加密凭据、连接状态、资产快照与交易限制|
|订单意图|属于某账户的一次确定委托，先在本地持久化再发送；拥有本地 UUID 和原客户订单标识，官方受理后另有官方订单标识|
|逐笔成交|以官方执行标识确认的实际成交；一笔订单可以对应多笔成交，重复证据不重复入账|
|任务|同一原执行窗口内持续生成订单的配置与进度；任务可关联多笔订单，但每笔订单仍有独立状态和核对过程|
|预留|本地尚未完成意图的资金或股票占用，不是新增现金，也不代表已经成交|
|名义持仓与账本|由本系统已确认成交和费用形成的本地业务记录，不自动覆盖外部交易|
|业务事件、审计与运行日志|分别记录业务推进、操作者及权限行为、服务运行与排障信息；均不是官方成交证据|
|原操作回执|记录某一次确定控制或管理指令的处理结果，不等于目标对象的最新快照|

API 的单笔下单可以在请求内经统一交易服务准备和派发；任务启动登记状态后由 Worker 推进。Worker 启动先恢复原订单，再推进任务与核对。Worker 离线、心跳不新鲜或账户尚未完成必要核对时，新交易受到阻断。

|查询与记录|概览、订单、逐笔成交、任务执行、本地名义持仓与账本、账户维度官方订单／成交历史、核对记录及业务事件|

### 查询范围与数据形态

本地订单、任务、名义持仓、账本、证券目录、管理用户／账户、审计和业务日志提供分页；普通账户列表、核对记录和未解决操作回执返回数组，没有同样的分页行为。普通账户与核对记录即使接受页码字段，也不按页截取。筛选字段的实际作用随资源不同，没有统一的任意排序功能。

本地订单和任务按创建时间倒序，证券目录与名义持仓按证券代码排序。订单详情包含该订单的成交与事件，任务详情包含相关订单、成交、事件及诊断；这些详情数组没有独立页长参数。本地成交没有独立的全局分页接口。

账户维度的官方订单／成交历史每次读取指定的一页，默认查询最近七天，默认每页 25 条、最多 100 条；七天是默认时间窗，不是本站接口设置的最大跨度。历史可包含本系统之外的交易，但读取不会自动生成本地订单、导入外部持仓成本或补齐完整现金结算。

官方订单 ID 与本地订单 UUID 不同，官方订单状态也不等于本地订单状态枚举。官方历史未提供的价格、数量、费用或时间保持空值；当前官方逐笔成交历史不提供费用分摊，不能据此得到每笔成交的实际费用。单页历史为空也不证明某个未知委托从未执行。

HTTP `/logs` 提供授权业务事件，管理员审计记录操作者与权限行为，服务器结构化运行日志记录进程与模块事件，三者用途不同。HTTP 接口不提供任意服务器日志文件下载。

## 5. 订单与批量任务怎样执行

### 单笔订单

后端区分三类交易意图：**限价订单按价格与股数提交，市价买入按本金提交，市价卖出按股数提交**。市价买入的费用独立于本金预留，不承诺获得指定股数；市价订单不承诺成交价格，只支持 DAY。

单笔限价订单直接提交明确价格与股数，不带任务使用的盘口取价规则、价格舍入策略或自动撤单配置。限价时段可为 `RTH`（常规时段）、`EXTENDED`（扩展时段）或 `24H`，有效期可为 DAY 或 GTC，实际支持仍受官方规则限制。市价订单不带限价或交易时段参数，不传时段也不表示官方承诺全天可成交。

预检逐项检查权限、证券规则、资金、费用、挂单数量和卖出库存，返回当次检查与占用估算，不创建订单、不预留资金，也不锁定价格或库存。真实提交先持久化原意图与本批预留，发送前再次核实证据。确定尚未开始发送的本地意图在 30 秒准备租约结束后可安全终止；开始发送以后，超时、重复标识或查无订单均不构成未执行证明。

新增交易同时受活动用户、活动账户、账户交易开关、管理员限制、平台急停、连接状态、Worker 健康和未结证据约束。账户已有未知提交、未确认取消、成交待同步、费用未核实或无法解释的预留时，不能继续产生新交易。

官方证券检查包括方向准入、股数步长、已提供的股数上下限、可核实的名义金额上下限与挂单数量。小数股与扩展时段还取决于官方相应能力；碎股 GTC 限价订单不能使用 RTH。官方未给某个股数边界不自动等于拒单，但缺失必要金额规则或证据冲突不构成通过。最终受理仍由官方决定。

### 批量任务

限价任务和市价卖出任务使用股数目标，市价买入任务使用本金目标；每批数量或本金可按固定值或随机范围配置。

限价任务支持固定价格、当次买一或当次卖一取价，取价档位不会因买卖方向自动替换。盘口转为两位限价时，可选择买向下／卖向上的方向保护、截断、四舍五入、向上取整，或拒绝非零超精度部分；默认采用拒绝策略。预检、预留和发送使用同一个处理后价格，原始报价及实际成交不被改写，手工固定价也不静默舍入。市价任务不使用这些配置。

|时间与批次设置|当前规则|
|---|---|
|计划开始|无预约时可立即启动；未来预约到实际开始时重新预检，不提前占款或生成订单|
|执行窗口|1–604800 秒，自实际开始形成原截止；暂停和进程重启不延长窗口|
|执行模式|默认串行，也支持定时连续|
|批次数量／本金|固定值或随机范围；随机股数的常规批次为整数，最后的 EXACT 尾量可涉及小数|
|批次间隔|固定或随机，范围 0.1–86400 秒、最多三位小数；任务自身还有间隔下限，默认 5 秒，不是管理员平台字段|
|可达到的频率|受当次校验、Worker、网络与官方共享限流约束；当前官方每 UID 每分钟 200 次限制不等于任务配置频率保证|

- **串行模式**：前单终态核对闭环后开始计算下一批间隔。
- **定时连续模式**：前单确认受理后开始计算间隔，不等待成交，允许存在多笔已确认挂单；资金、库存及未知结果门禁仍独立生效。

批次计算同时考虑真实已成交量和活动订单的未成交量，受理量不等于完成量，手续费不计入市价买入的本金目标。活动订单占满目标时等待结算，终态未用本金或股数重新成为剩余量。

- **EXACT 尾量策略**：最后一批裁剪到剩余目标，不向上凑量；尾量或余款仍受官方最小量、金额、步长及碎股规则约束，不合法时拒绝保存或在执行中暂停说明。
- **FIXED 尾量策略**：剩余量不足本次批量时，不生成超目标订单，继续等待原窗口，不直接宣布完成，也不单因这一情况自动暂停。

|挂单策略|实际含义|
|---|---|
|KEEP，默认|保留原挂单；暂停、停止和窗口结束本身不要求撤单，订单仍可能按交易所 DAY 等规则失效|
|AFTER_TIMEOUT|每笔订单自原确认受理时间起 1–3600 秒触发已授权的超时撤单；人工暂停后仍生效|
|AT_TASK_END|窗口到期或明确停止任务时处理原挂单；普通暂停、账户限制、用户禁用或平台急停本身不触发该策略，后来实际到期仍按原策略处理|

自动撤单先核对原单并持久化取消开始证据，结果未知后只核对而不重复发送。限价任务支持 DAY／GTC，订单有效期与任务执行窗口不同；单笔订单不附带任务的自动撤单策略。

暂停不延长原窗口，重启不重置已经过去的时间，也不补发错过的周期。任务停止或到期，与订单终态、费用确认、库存核实及预留释放分别记录。

保存或编辑任务只保存完整配置，不自动启动，不为整份目标锁定资金。启动和继续会重读规则、资金或库存，并复核未结证据与原预留；启动成功也不表示第一笔订单已经发送。

只有 CREATED、READY、PAUSED 的任务允许编辑。任务实际开始后，账户、证券、方向和订单类型固定，计划开始时间不能真实改变，窗口只能保持或缩短；目标不能低于已经成交量与活动委托剩余量之和。编辑不撤换原挂单、不自动继续，修改超时策略仍从原受理时间计算，不从编辑时重新计时。

## 6. 资金、持仓与业务记录分别代表什么

|数据|来源与含义|
|---|---|
|买入资金|官方 Funding 钱包 USDC，是买入预算来源；每次执行结合当次资金、费用估算及既有占用检查|
|Spot 资产|只读展示，不并入 Funding 购买力；系统不自动划转或换币|
|官方股票库存与持仓候选|来自所选账户的官方数据；可卖证据包含证券身份、可用股数与来源时间，持仓候选不等于已经取得当次卖出许可|
|本地名义持仓与成本|根据本系统已确认成交形成，不代表账户全部外部持仓，也不补造外部买入成本|
|本地账本与费用|记录本系统交易及核对结果；预留费用是估算，实际费用以官方证据为准，不等同于完整官方结算或盈亏报告|

USD 报价、USDC 资金与本地名义金额是不同口径。价格、股数和本金以十进制字符串传输并采用精确十进制运算，不以二进制浮点累计金融结果。

|数值或时间|精度与含义|
|---|---|
|提交限价|最多两位小数，不因盘口或成交均价位数更多而放宽|
|请求股数、股数目标与固定批次|最多十位小数；实际证券步长和碎股能力另行约束|
|市价本金|最多十二位整数、十八位小数；本金目标不含费用|
|任务间隔|JSON 数字，最多三位小数秒|
|计划开始时间|带完整秒的 UTC `Z` 时间；新建或真实修改时最多六位去尾零后的有效小数秒，超出拒绝而不舍入；未修改的原时间保留原精度|

买入仅扣除本地尚未发送意图的资金占用，不再次扣减交易所已经冻结的金额。卖出来源使用当前账户及凭据对应的 Funding 可用股数，结合精确证券身份映射核实，不加入锁定或冻结量；本地名义持仓不是可卖库存。资金和库存采用本地 15 秒取证有效期策略，这不是交易所原子同步或更新时效承诺。

空结果、读取失败、未知值与已确认零值具有不同含义。官方库存读取也没有与订单状态原子同步的保证；有成交的卖单在最终费用和库存证据闭环前，仍可能保留同证券卖出门禁。

### 检查、同步与账户核对的区别

连接检查读取官方规则、私有连接和钱包，保存该次连接结果；检查失败也可以形成已完成的检查回执，表示失败事实已经保存，并非连接成功。检查不自动开启账户交易。

资产同步保存本次钱包快照或读取失败标记。失败时可能保留旧快照与旧时间供历史说明，但当前可用资金仍为空；同一原操作 ID 返回该次冻结结果，不因后来网络恢复而自动变成一次新同步。

账户核对先固定本次本地订单、任务集合及官方历史查询上界，再核对这些原对象；冻结的是处理范围，不是官方资产或成交快照。中途中断可能留下部分订单已结算、原核对尚未完成的状态，后续恢复仍使用原范围。

|账户核对记录|含义|
|---|---|
|DIFFERENCE|仍有未知、未释放或库存待核对订单，或官方历史存在不属于本地已知订单的记录|
|UNAVAILABLE|没有可用资金钱包或官方历史读取失败；如果同时存在前述差异，差异状态优先|
|PARTIAL|已检查的部分完成，但不表示官方总持仓与完整现金结算全部一致|

当前账户核对没有“全量一致”结论。原核对回执完成，与核对记录是否存在差异，是两个维度。

## 7. 安全、状态与恢复机制

会话使用 HttpOnly Cookie，有效期为 8 小时；登录响应返回用户身份和当前 CSRF，不返回会话令牌本身。除登录外的写请求使用与会话绑定的 `X-CSRF-Token`，包括登出、预检、撤单和核对。服务端同时执行精确 Origin、角色、所有权及限流校验。退出撤销当前会话，改密撤销该用户全部会话。

跨源访问采用携凭据的请求，Cookie 默认 SameSite 为 `strict`；真正跨站的使用仍受 HTTPS、Cookie 配置和浏览器第三方 Cookie 策略约束。SSE 沿用会话和来源校验，因其是读取通道，不使用写请求的 CSRF 头。

密码采用安全哈希，交易所凭据在服务端加密保存；对外接口不返回 API Key、API Secret、Listen Key 或签名。实际更换凭据前会检查未完成订单、未释放占用、未核实费用及未结束任务；替换成功后关闭交易并重新验证，不能据此证明新旧 Key 属于同一官方账户。

### 三类状态

系统分别记录**订单状态、任务状态和原操作回执状态**。HTTP 成功、指令已应用、订单已受理、实际成交、费用与库存已核实，是不同层面的事实；某个操作可以已经应用，但后续外部读取仍然失败。

**本地订单状态**

|状态|含义|
|---|---|
|PLANNED|原意图与本地预留已落库，不表示已经发送|
|SUBMITTING|提交开始已经记录，结果尚未完全确认|
|ACCEPTED|官方受理已确认，尚无已入账成交或成交证据尚待对齐|
|PARTIALLY_FILLED|部分实际成交已核实，剩余委托仍可活动|
|CANCELING|取消开始已记录，原单终态尚未确认|
|UNKNOWN|提交、取消、官方状态或证据冲突尚未核实，不是确定失败|
|FILLED|委托成交终态，最终费用或卖出库存仍可能待核实|
|CANCELED|官方已撤销剩余委托，已发生的部分成交仍然有效|
|REJECTED|明确官方拒绝，或有证据的本地未发送中止，具体由原因区分|
|EXPIRED|订单按官方规则失效，可已有部分成交，不等于任务窗口状态|

订单终态不自动等于费用、库存和预留全部闭环。订单没有编辑委托、重试提交、强制成交或强制释放的公开动作；取消开始之后仍只核对原单，不能因旧快照重新显示已受理而再次撤单。

**任务状态**

|状态|含义|
|---|---|
|CREATED|配置已保存，未启动、未锁资金；当前新建任务直接进入此状态|
|VALIDATING|公开定义的预检中状态，不表示订单受理|
|READY|待启动状态，不表示已有受理订单|
|SCHEDULED|未来开始已登记，到时重新预检|
|RUNNING|在窗口内推进，也可能等待间隔、结算或不足一批的 FIXED 尾量|
|PAUSED|停止新增批次，原挂单与原截止保留|
|RECONCILING|原订单证据核对中，是否具有自动继续资格取决于具体原因|
|RECOVERY_REQUIRED|未知结果、硬冲突、未闭环或安全停止形成的人工处理门禁|
|STOPPING|永久停止意图已登记，原订单和占用仍待处理|
|COMPLETED|真实成交目标完成，原订单与相关核对闭环|
|EXPIRED|原窗口结束、目标未完成，原订单已闭环|
|STOPPED|永久停止后原订单已闭环|
|FAILED|失败终态，不是可直接重新启动的配置|

启动只接受 CREATED／READY，继续只接受 PAUSED；RECONCILING／RECOVERY_REQUIRED 先经核对，由后端确定是否能进入运行或暂停状态。终态只保留核对，不重新打开窗口。公开接口没有任意指定任务状态的动作，也没有要求新建后先人工改为 READY 的步骤。

**原操作回执状态**

|状态|含义|
|---|---|
|PROCESSING|原执行者仍可能在处理，防重复保护保留|
|UNKNOWN|没有可信终态，操作可能已部分应用，原范围和占用继续受保护|
|CONFLICT|公开契约保留的未解决状态；普通 HTTP 409 或原 ID 冲突错误不自动把回执改成此状态|
|REJECTED|这一次原操作已被证明未应用，不代表目标没有其他未知操作|
|SUCCEEDED|该类操作定义的本地应用或核对流程完成，不统一等同于连接成功、资产可用、订单撤销或任务完成|

回执还包含处理阶段、结论和冻结结果。例如“控制已应用”只说明本地控制已提交；“检查完成”可以保存连接失败；“同步完成”可以保存读取失败标记；“目标已是其他终态”也不等于撤单成功。当前对象后来发生变化，不会重写这次原回执的结果。

### 原标识与恢复边界

下单使用 `Idempotency-Key` 绑定原订单意图，该键为不含控制字符的 1–200 位字符串；同一键不能变成另一笔订单。撤单、任务控制、账户检查／同步／核对、用户状态或管理权限变更、账户平台限制及平台设置使用 UUID 原操作标识，绑定实际操作者、目标及参数，并保留持久回执。

结果未知时，恢复流程围绕原标识核对，不自动创建第二个交易意图，不因超时、查无记录或页面关闭释放未确认占用。读取原回执只是查询既有证据，不重新执行原动作；原操作核对仅推进该类型允许的恢复过程。继续尚未完成的账户核对仅限原操作者，且使用原本冻结的范围。

账户创建／保存、任务创建／保存、用户创建、登录、退出和改密没有上述统一持久回执。原订单核对也没有新增一份通用操作回执，其结果仍属于原订单证据。因此并非所有写操作都有相同的跨刷新恢复能力，当前对象快照不能证明某次原请求的终态。

实际成交以唯一执行标识去重，订单、成交、名义持仓、账本和业务事件在结算事务中更新。重复或陈旧证据不重复入账，也不倒退已经确认的终态。

任务恢复区分证据待同步与人工处理门禁：符合自动恢复条件的运行任务，在阻断证据闭环后按原时钟继续；人工暂停、停止、到期、安全限制或硬冲突不会因此被自动解除。

## 8. 对外接口与运行形态

### HTTP 与公开契约

后端提供 **52 个明确的方法／路径组合**，其中包含两路 SSE。业务路径位于 `/api/v1`，健康检查为 `/healthz`，默认本机监听地址为 `127.0.0.1:3020`，实际地址由部署配置决定。主要交互使用 HTTP／JSON，成功响应通常包含 `data`，错误通常包含 `error`，部分操作另带 `operation` 原回执；JSON 请求体上限为 64 KiB。

公开契约位于 `backend/contracts/client.d.ts` 与 `backend/contracts/validation.ts`，分别提供 TypeScript 客户端声明和公开校验规则。HTTP 协议不绑定特定客户端框架；当前没有已提供的 OpenAPI／Swagger 描述，静态声明也不穷尽所有错误、流事件及运行时空值。

### 两路实时通道

- **业务 SSE**：通知哪些业务资源发生变化，不承载完整业务账本。
- **行情 SSE**：提供指定账户／证券的报价与行情状态，不作为成交账本。

两路均采用 SSE 默认 `message` 帧：业务载荷为资源刷新提示，行情载荷按 `quote`／`status` 分类，不是同名的独立 SSE 事件。业务流首次连接和重连会提示重新读取资源；行情流先取得 REST 快照并中转官方行情，缺少有效行情推送时后端补读，不以旧值伪造实时状态。

同一用户的两路流合计最多 6 条活动连接，按单 API 进程共同计数，不是每类流或每个标签页各 6 条。两类建流分别有每用户每分钟 30 次限制。流还持续受会话、用户与账户授权状态约束，已建立连接不表示授权永久有效。

当前没有事件补播、历史游标或全部中间变化必达的保证。连接保活只说明传输仍有字节，不证明 Worker 正常、官方行情新鲜或交易可以执行；业务查询和原单核对分别提供当前业务记录与交易证据。

### 运行与生命周期

API 与 Worker 使用数据库持久化状态。首次连接时自动核对迁移日志与哈希、加锁执行缺失迁移；版本不匹配、资源缺失或迁移失败会阻断启动。首次建库与账号初始化是独立的显式操作。运行信息包含健康、心跳、结构化脱敏日志和只读资产诊断。

后端可独立安装、构建和运行，不托管前端静态文件，也不附带 Docker、NGINX 或主机部署配置。

## 9. 当前能力边界与验证状态

- **未提供的功能**：忘记密码、管理员重置密码、任意资源删除、独立本地全局成交分页、完整官方盈亏计算，以及行情研究、回测和虚拟交易环境。
- **整份任务预算**：原始需求包含买入任务整份预计资金评估。当前保存不核实或锁定整份目标资金；启动按实际分支检查单批或资金来源，实际执行再次预检。这些检查不等于整份目标预计资金评估，该项原始要求尚未闭环。
- **迟到 401 与新会话**：旧会话请求的 401 可能带删除 Cookie 的响应头，在新登录之后到达时影响同一作用域的新 Cookie。独立浏览器探针观察过这一机制，尚不是本项目 API／数据库或跨标签页端到端复现，也不表示所有部署必然发生或问题已经修复。
- **错误表达与原 ID 冲突**：不存在和无权访问的错误差异可能暴露对象存在性；原操作前置拒绝与正常执行路径的输入归一化差异，可能使同一请求对应不同指纹并触发原 ID 冲突。相关结论包含源码分析，后者尚缺完整链路复现。
- **静态契约与导出**：静态声明未覆盖全部错误、SSE 载荷及运行时空值，例如缺 Worker 心跳时相关时间可能为空。契约导出曾有一次原因未定位的字节校验失败，后续独立导出一致不等于该问题已修复。
- **部署与实盘证据**：现有产品资料将 3.0.0 标记为尚未部署。历史只读查询、隔离测试和旧版本部署，不构成当前版本的完整真实买卖、成交、费用、撤单及故障恢复验收。系统不代签股票风险声明。
