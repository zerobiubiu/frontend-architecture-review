## 三、执行方法

每个问题采用以下流程：

1. 核对当前源码、调用方、相关测试和真实契约。
2. 给出“成立／部分成立／已修复／不成立／待验证”的判断。
3. 对成立的问题，优先添加能在修复前失败的回归测试，记录失败原因。

不要为了通过测试而弱化业务约束；但原测试若固化了错误预期，应说明依据后纠正预期，而不是保留错误行为。不得通过 skip、删除断言、扩大 any 或忽略错误来伪造通过。

## 四、逐项修复要求

### REV-01：区分 HTTP 尝试与原意图结果

重点文件：`src/services/api/errors.ts`、API 类型及对应测试。

复核并修正“无 operation 的所有 4xx 都归为 rejected”的规则。401、403、404、409、422、429 和 `operationAccepted:false`，都不能单独证明同一原 ID 的历史操作没有执行。

需要明确区分本次发送前的本地拒绝、本次 HTTP 尝试被拒绝，以及原订单／原操作已确认未应用。原意图终态必须绑定正确的原 ID 和可信业务证据；不得因后续请求失败清除既有 unknown，也不得自动换 key。

验收：构造“首次结果未知，后续返回无回执 4xx／operationAccepted:false”的测试，分类结果不能提供“原意图已确认未执行”的结论。恢复系统尚未实现时，用最小调用方测试验证不错误解锁，不为此新建完整恢复系统。

### REV-02：回执缺失、有效、无效必须可区分

重点文件：`src/services/api/response.ts`、`request.ts`、`types.ts`、`errors.ts`。

不能将缺失 operation 和存在但无法解析的 operation 都转换成 null，再把后者按普通成功处理。至少在语义上区分 absent、valid、invalid；具体类型设计自行决定。

分别解析 HTTP 状态、data、error 和 operation。畸形 error 不得直接抹掉可独立验证的回执；畸形 operation 也不得变成 applied。保留必要的诊断与恢复线索，但不得将原始敏感响应自动写入持久日志。

可信原意图判断还需要与请求的 ID、kind、target 对应；未知 kind 不能只靠 SUCCEEDED 直接当作业务成功。非回执型端点也应按其具体协议判断，不能统一推断所有 2xx 都代表交易完成。

验收：200＋畸形 operation、未知 status、缺 id/kind、有效回执＋畸形 error、原 ID 不匹配、允许的新扩展字段。确认未知结果不会被误判，并且已解析证据不会无故丢失。

### REV-03：无效纽约草稿和未解决 DST 必须阻止表单提交

重点文件：`src/components/ui/utc-datetime-field.tsx`、Playground RHF 适配、组件与 E2E 测试。

修复 nyDraft/zoned 与父表单 UTC value 脱节的问题。界面显示格式错误、春季不存在时间或秋季重复时间未选择时，父表单不能继续静默提交旧 UTC 或把未决编辑当作“未设置”。

建立明确的字段编辑有效性协议，并接入 RHF 提交校验。不要只显示错误文字；不要把所有非法草稿改为空串，因为可选字段允许空串时仍会绕过校验。

同时处理：纽约模式的外部错误展示和输入 ref、外部 reset/value 更新、时区切换的草稿同步、明确清空语义，以及 disabled/readonly 对模式切换、候选 RadioList 等全部子控件的约束。

验收必须使用真实 RHF 提交回调，而不只是检查错误文案：

- 原值合法，改成 `2026-03-08 02:30:00`，提交回调不得执行。
- `2026-11-01 01:30:00` 未选择候选，提交回调不得执行。
- 可选字段原值为空，输入无效草稿，同样不能通过。
- 合法选择、明确清空、reset、外部值变化和模式切换均符合约定。
- disabled/readonly 下不能通过候选控件改值。

### REV-04：建立符合协议范围的十进制计算上下文

重点文件：`src/lib/decimal/decimal.ts` 及对应测试。

核对当前锁定版本 decimal.js 的默认计算精度。不要把“构造时保留字符串”当作“后续加法无损”。使用项目专用 Decimal.clone 上下文或等价隔离方案，明确精度、舍入、输入边界和累计规模；避免修改所有依赖共用的全局 Decimal 配置。

必须验证：

```text
999999999999.123456789012345678
+ 0.000000000000000001
= 999999999999.123456789012345679
```

同时覆盖尾数进位、多行累计、正负抵消和最大协议范围。不能随便设置一个较大的 precision 就宣称支持无限精确计算；应解释为何满足当前受支持范围，范围之外如何处理。

检查 normalizeDecimalText 的输出闭包：若约定是不含指数的十进制文本，那么 `0.00000001` 等值规范化后仍应可由同一解析器读取且数值不变。展示舍入不得回写提交值。

### REV-05：时间校验与后端契约对齐

重点文件：`src/lib/time/instant.ts`、`zoned.ts`、时间字段及测试。

重新阅读后端计划时间校验和既有值保留规则。按其真实契约验证有效小数秒，而不是机械按原始小数总长度限制。

至少核对：

| 输入 | 按审查报告应验证的行为 |
|---|---|
| `2026-11-10T01:23:45.123456Z` | 接受并保留原串 |
| `2026-11-10T01:23:45.123456000Z` | 尾零不增加有效精度；原串保留 |
| `2026-11-10T01:23:45.0000000Z` | 按有效精度规则接受 |
| `2026-11-10T01:23:45.1234567Z` | 新输入拒绝 |
| `0000-01-01T00:00:00Z` | 拒绝 |
| `2026-02-30T00:00:00Z` | 拒绝 |

新输入校验与服务端允许的“未改历史原值透传”分开处理，不设置任意绕过校验的开关。不得用 Date 毫秒值判断微秒级等价，也不得修改后端规则迎合控件。

### REV-06：修复 color-scheme 层级覆盖并验证真实颜色

重点文件：`src/styles/index.css`、主题源与生成物、主题 E2E。

复核 components 层无条件 `:root { color-scheme: light dark; }` 是否覆盖 astryx-theme 层的显式 light/dark。优先移除重复主题拥有者，让主题统一决定 color-scheme。

不手工修改生成 CSS，不通过 !important 掩盖层级问题。需要变更主题时修改源并使用现有命令生成，执行 theme:check。

在完整项目真实浏览器中验证四种系统／手动组合，并断言 computed styles：系统浅色＋显式深色、系统深色＋显式浅色，以及同向组合。覆盖页面背景、Card、输入框和 Dialog/Drawer/Toast Portal。

仅检查 data-theme 属性或生成截图不算通过；需要对计算后的颜色或可重复视觉结果做断言。保留系统模式随系统偏好变化的行为。

### REV-07：验证并阻止敏感写操作离线延后发送

重点文件：`src/app/providers/query-client.ts`、必要的最小写操作适配和测试。

依据 bun.lock 中实际 TanStack Query 版本验证 `retry:false` 与 `networkMode:'online'` 的区别，不把机制推断直接写成项目已复现。

为未来敏感写操作提供最小 fail-fast 边界：离线时不进入恢复网络后会自动发送的队列。网络恢复不视为用户再次确认；不得持久化、恢复或自动重放敏感 mutation。

不要仅机械修改一个 networkMode 就宣称解决，应验证所选配置与提交门禁组合。会话代次、账户和确认有效性尚无完整实现时，可使用注入上下文做最小测试，不开发第二阶段系统。

验收：离线触发模拟敏感操作 → 恢复网络 → 未重新明确确认时 Fetch 仍为 0 次；另测等待期间会话／账户变化。已经可能发出的请求超时或取消，仍保持未知，不得误报未发送。

## 五、报告第 10 节补充事项

逐项记录处置，不能只修七个主问题后遗漏这些边界：

1. **健康接口：**根据真实 `/healthz` 契约保留 503 响应中的 data，区分“HTTP 非成功”与“健康详情可读取”，不能将所有非 2xx data 泛化为业务成功。
2. **SSE：**复核 refresh.resources 是否允许缺省；区分缺失、空列表、未知资源和畸形帧，不一律吞成“没有变化”。按明确协议提供有界收敛信号；本轮不实现完整 SSE Manager，也不能每个异常帧都无限全站刷新。
3. **表格：**没有排序回调或服务端不支持排序时，不展示假可用的排序按钮；补真正改变 totalItems 的 rerender 用例。分页仍由调用方唯一拥有。分组表头暂不支持可明确限制，不强制扩展组件。
4. **Mock：**标明演示模型与真实契约的边界；检查 reduceOnly、大写 START、模拟字段错误等示例，不得作为已完成后端契约对接的证据。优先使用中性演示模型或真实契约夹具，避免后续误复制。
5. **验证可信度：**正式验收不无条件复用身份不明的开发服务器；theme:check 纳入验收。覆盖率无阈值时按事实报告，不宣称达到门槛。Bundle、字体、sourcemap、多浏览器等按报告记录，可后置的不要扩大成本轮重构。

补充事项如不适用于当前源码，提供证据；暂缓项写清理由和启用前条件，不得标为已解决。
