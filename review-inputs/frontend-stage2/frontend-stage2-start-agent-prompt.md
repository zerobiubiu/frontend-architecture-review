## 四、优先接入后端已有 Hono RPC 契约

### 4.1 使用现有产物，不重新设计 DTO

用户已经提供以下契约生成链路，应在当前源码中核对实际导出与路径：

```text
backend/src/server/app.ts
    导出 AppType = typeof app
             ↓
backend/scripts/contract-entry.ts
    使用 hc<AppType>()，生成展开后的客户端声明
             ↓
后端公开客户端声明 + 公开校验规则
             ↓
api-contracts/
             ↓
frontend/ 本地 file: 依赖
```

前端依赖方式采用：

```json
{
  "dependencies": {
    "@project/api-contracts": "file:../api-contracts"
  }
}
```

hono 另行添加为前端运行依赖，版本按实际后端锁定值核实。消费类型的基本方向是：

```ts
import type { ApiClient } from '@project/api-contracts';
```

后端产物是唯一公开 DTO 来源。前端不得直接导入 backend/src，不得复制手写一套请求、响应 DTO，也不得引入后端服务、数据库、SDK 或密钥配置。

先复用已存在的 api-contracts 包或现有导出布局。若不存在，最小封装 backend/contracts 中已有公开产物，建立正确的 package.json、types/exports 和必要运行时导出。生成文件只同步，不手改其内容。

只需要一个可重复的同步/检查流程：记录产物来源，能检查源产物与消费包一致即可。确认当前 Bun 对 file: 依赖的实际解析及更新行为，避免源文件已更新而前端仍消费旧副本。不建立复杂发布流水线。

若必须重新生成后端声明，只在审查命令确认无运行时后端副作用、且不会改写 backend/ 的情况下运行现有纯生成能力；否则使用已有产物并记录后端待导出事项。绝不能运行整个后端入口来取得类型。

### 4.2 正确区分 ApiClient 与 AppType

本项目优先消费已经展开的 ApiClient 类型，不强迫前端重新获得 AppType 或重新实例化整棵后端类型图。

不得机械写成 hc<ApiClient>()：先看真实声明，已经展开的客户端类型不是 Hono 应用类型。

如契约包已有类型化客户端工厂，直接复用。如只有 ApiClient 声明，在唯一客户端创建位置完成最小的 hc 运行时与生成类型绑定；必要的类型连接集中在这一处，并通过编译正负例和实际请求路径测试验证。不要把 any、双重断言或不安全强转散落到业务代码中，也不要声称单次类型断言等于运行时校验。

不另建接口代码生成器。业务请求类型优先从生成客户端对应方法派生；UI 表单状态与页面展示模型可以独立定义，但必须明确不是第二套 API DTO。

### 4.3 声明与运行时产物边界

.d.ts 只供编译与类型检查，不进入浏览器运行时。公开 Zod 校验规则若实际导入使用，则需要真实、浏览器可用的模块，不能只提供声明后在运行时导入不存在的值。

检查产物是否引用 backend/src、Bun 服务端能力、数据库包或不兼容的声明语法。契约包应能在 frontend 当前 TypeScript 版本下被消费；出现问题先做局部兼容分析，不盲目升级整套工程。

实际校验 RPC base URL 与声明路由层级，尤其防止 /api/v1 被重复拼接或遗漏。根级 /healthz 与 /api/v1 下业务路由分开处理，以真实路由为准。

必须补类型负例：不存在的路由、错误参数、缺少必填参数不能通过 typecheck。正确请求与响应推导必须保留，不得将整个客户端退化成任意字符串调用器。

## 五、RPC 接入现有 API 安全边界，不另建一套语义

目标数据流：

```text
页面 / Auth Feature / TanStack Query
                 ↓
类型化 Hono RPC 调用
                 ↓
同一套受控 Fetch 传输
                 ↓
原生 Response
                 ↓
现有信封 / receipt 三态解析 / DTO 边界校验
                 ↓
ApiOutcome 与领域判断
```

沿用现有 services/api 分层，只做必要调整。已有 client.ts 的名称若与生成 ApiClient 冲突，可以局部别名处理，不批量搬目录。

Hono 客户端的自定义 fetch 必须保持原生 fetch 的返回契约，返回 Response；不能把现有返回 ApiOutcome 的 requestJson 直接当作 fetch 注入。允许抽取共享的底层传输及响应消费函数，让 RPC 与既有测试共用同一实现，不保留两套逐渐分叉的生产错误处理链。

每次调用必须最多发出一次真实请求。禁止 RPC 发一次、旧 API Client 再发一次；禁止为了取得类型或回执追加重发。响应体只消费一次，超时/取消范围要覆盖需要等待的响应体读取，不只保护响应头。

保留动态 Cookie/CSRF 注入、AbortSignal、超时、请求来源、会话代次和 attempted 语义。参数和原操作 key 不可由底层任意覆盖。原生 fetch 发生后超时/中断仍是未知，不能伪装成发送前拒绝。

必须保留并回归这些不变量：

- 非 2xx 仍解析和保留回执；health 的 503 data 不冒充 success。
- receipt 保持 absent/valid/invalid，不因错误信封损坏抹掉有效回执。
- attempt 与 intent 分离；无回执的 4xx、operationAccepted:false 不证明原意图未执行。
- classifyWriteOutcome 与 receiptMatchesRequest 继续要求完整原请求身份；身份必须来自发送前上下文，不得从响应反构造。
- 匹配 SUCCEEDED/REJECTED 的原有语义保持；回执终态不等于目标业务成功。
- 保留敏感写门禁，不自动重试、离线排队、持久化恢复 mutation 或换 key 重发。

认证接口不属于八种 operation 回执业务时，使用其专用协议处理，不为登录、退出虚构操作回执或强行调用回执终态分类器。

本阶段真正使用的身份、权限、CSRF 等字段必须做必要运行时验证。优先复用公开 Schema；若后端没有对应响应 Schema，只对本阶段实际使用的安全关键字段建立最小防御性校验并记录缺口，不声称 RPC 静态类型已验证网络数据，也不预造全部业务 DTO。

业务组件不再自行拼路径调用 fetch。平台级 SSE 保持 EventSource，不强行塞入 JSON RPC 请求管线。Hono 当前版本若有非 2xx 自动抛错的便利函数，也不能绕开现有响应保留语义。

## 六、登录、会话恢复、退出与 Session Epoch

### 6.1 本阶段接入的认证流程

读取真实 auth 路由和公开契约，按实际字段实现登录、/auth/me、退出。不要猜测用户名字段、角色枚举、CSRF 字段或退出响应形状。

登录页面用现有 Astryx + RHF + Zod；密码不 trim、不持久化、不输出日志。登录失败、限流、网络不可达和响应异常分别展示，不统一提示密码错误。returnTo 只能采用经过校验的站内允许地址，拒绝绝对外站地址和协议相对地址。

刷新时用 /auth/me 恢复会话。明确区分初始化、检查中、已认证、未认证、暂时不可用及退出未确认状态；网络超时和 5xx 不等于未登录。身份未确认时，不展示敏感旧缓存，也不开放需要认证的操作。

核对页面刷新后的 CSRF 获取机制。只按真实契约取值，内存保存；不得把密码、会话令牌或 CSRF 放入 URL、localStorage、持久化 Query。后端没有必要能力时记录具体缺口，不能伪造 token 或绕过校验。

退出时立即阻止新的受保护操作，关闭 SSE、取消旧请求、清敏感缓存并推进会话隔离。若退出网络失败，明确“本地已清理，但服务端注销未确认”，不得马上自动调用 /me 又无提示地恢复为已登录，更不得把超时当作注销成功。提供明确的重试/重新验证入口，认证流程不自动重放写请求。

修改密码及用户管理不在本次范围，不创建不能工作的菜单入口。

### 6.2 会话隔离

建立单一 Session Manager，管理身份确认状态、epoch、CSRF 和生命周期；完整用户 DTO 明确一个数据拥有者，不在多个 Store 中重复保存整份用户信息。继续使用现有一个 QueryClient，不引入状态管理库。

登录流程开始、退出、身份切换或会话失效时按统一规则隔离旧请求。请求和 SSE 捕获发起时的 epoch；回调应用结果前重新核对，旧结果不能进入新会话 UI、Query 或全局错误处理。先捕获再发送，不能返回后才读取最新 epoch 给旧结果贴新标签。

对受保护 Query 明确 session/user/account 作用域；会话切换时取消、清理及失效协同处理。旧 401 不能退出新会话；同样防御旧成功响应、旧 403、旧 SSE 和旧 mutation 回调。不跨身份/账户复用敏感 placeholderData。

认证状态变化应串行化或有明确竞态处理，防止登录、退出及 /me 交错互相覆盖。前端 epoch 不能阻止浏览器处理迟到的 Set-Cookie；如后端仍有迟到 401 删除新 Cookie 的风险，保留为真实联调/发布前条件，不能声称前端已彻底修好。

可用一个轻量 BroadcastChannel 发送“会话可能变化”的通知。不要广播 token、用户数据或把其他标签的 epoch 当本页权威值；收到通知后本页隔离旧状态并按策略验证身份，避免广播回环。本阶段不实现跨标签共享 SSE 主节点。

## 七、AppShell、权限和页面范围

沿用 Astryx 主题、Tabler 图标和 Tailwind 布局，不重新设计颜色系统，不手改主题生成物。采用清晰、克制、信息密度适合交易管理产品的应用外壳。

顶栏左侧为侧栏折叠按钮与连接状态；右侧按通知入口、头像、用户名、用户菜单组织，退出放入用户菜单。未接入通知中心时不显示虚假数量或业务通知。API 可达、会话有效、业务 SSE 已连接是不同状态；不能因 EventSource open 就显示“全部业务已同步”。

侧栏沿用“工作台 / 交易执行 / 账户与账本 / 系统管理”的分组方向。仅开放本阶段可用页面，未来功能要么不显示，要么明确标为未开放且不创建假业务数据。管理员不被默认视为拥有所有交易员操作权限；具体角色及专项权限从当前后端身份契约确定。

实现 /login、受保护的工作台入口、必要的无权限/404/错误页面；保持 /dev/playground 仅开发环境注册，不破坏第一阶段回归。工作台只显示已确认的当前身份、角色和基础连接状态，不做虚构资产、盈亏或交易统计。

导航、路由直接访问和权限变化使用同一能力判断。受保护路由不能在会话初始化完成前闪现内容；隐藏菜单不代替路由守卫，前端守卫不代替后端授权。可用隔离测试路由验证角色边界，不为了测试建设整套管理员页面。

布局支持桌面折叠侧栏与移动端抽屉、键盘操作、焦点归还、Light/Dark/System。实际使用现有组件 API，不根据名字猜测不存在的 Astryx 组件。

## 八、最小业务 SSE 与 Query 收敛

复用现有 SSE 解析层，按真实 GET /api/v1/events 契约接入原生 EventSource；行情流本阶段不接入。

每标签、每个有效会话最多一条业务连接。已认证且 CSRF/身份初始化按契约完成后才启用；退出、身份变化、销毁时关闭连接，移除监听器和定时器。React StrictMode 重挂载不得泄漏连接或重复订阅。旧 epoch 消息不得作用于新会话。

区分默认 message 中的业务 error 帧与 EventSource 传输 error。后者不能凭空提供 HTTP 401/429 状态；不得统一解释成退出登录。按真实错误码对明确授权终止执行关闭，对可恢复故障采用单一、受控的重连策略；避免原生自动重连和自建重连同时生效。必要的 /auth/me 复核也要限频。

核对后端当前连接配额和建连限制，限制重连频率。多标签超额时应降级提示，而不是不断重连占满配额。本阶段不实施 BroadcastChannel/Web Locks 的连接共享架构。

资源通知只用于失效与重读，不直接作为订单、资产或任务数据。scope=all 只映射到当前会话、授权范围内、已注册的有限资源集合；未知资源和畸形帧不能引发无界全站请求。

为已注册的 Query 提供资源映射；通知可标记非活动缓存失效，但只主动重读活动 Query。不为不存在的业务 Feature 预造 API 或查询。用 Mock 查询验证映射及授权过滤即可。

必须保留在途变化：GET 执行中收到 refresh，记录 dirty/版本计数，结束后尾随重读；短时间通知合并，不吞掉最后一次变化，也不形成无限刷新循环。退出或 epoch 变化后取消尾随任务。

首次建连、重连、窗口恢复等场景执行必要的 REST 收敛，并为活动数据保留有界的补充刷新策略；只做失效通知不能承诺强一致或补播。没有活动消费者时，不为演示发起全站查询。完整订单/operation 独立轮询与恢复留到业务阶段。

## 十、测试与真实环境边界

默认使用当前 MSW、Mock Fetch 和本地受控协议桩。若需要真实浏览器 Cookie/SSE 行为测试，可以使用无数据库、无官方 SDK、无交易路径的本地测试服务器，但必须与 backend/ 分开并清楚标记为协议桩，不冒充后端联调。

不自动启动现有 backend。只有存在另行明确授权、已确认无真实资金副作用的隔离后端时，才记录真实联调；没有则继续完成前端与协议测试，将对应结果标为未执行。
